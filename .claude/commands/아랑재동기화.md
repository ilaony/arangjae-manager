에어비앤비·부킹닷컴에서 **세 숙소**의 신규·변경·취소 예약을 찾고, 앱(Firestore)과 대조해 차이를 보고한다.

메일 조회 범위: 최근 **$1**일 (비어 있으면 7일). **단 캘린더 대조는 미래 전체**를 본다 — 메일이 안 온 예약이 실제로 있었다.

## 가장 중요한 규칙

**대조 결과를 먼저 보고하고, 사용자가 승인한 뒤에 쓴다.** 조회·대조는 승인 없이 진행하되, Firestore 쓰기는 절대 먼저 하지 않는다. **단 아래 `## 자동 처리`의 조건을 전부 만족하는 건만 예외**로 승인 없이 쓴다.

이유: 차이가 단순 반영이 아닌 경우가 많다. 실제로 나온 유형들 —

- 앱 이름이 `ㅇㅇ`·`dd`·`Dd` 같은 플레이스홀더여서 덮어쓸지 판단이 필요했다
- 변경 요청이 **이미 앱에 반영돼 있어** 또 쓰면 되돌릴 뻔했다
- 게스트 국적이 선택 목록에 없어서 **코드 수정이 필요**했다 (마카오, 뉴질랜드, 이탈리아·이스라엘·오스트리아)
- 거주지가 **동반자 것만** 표시돼서 일행 기준으로 추정해야 했다

기계적으로 쓰면 틀린 쪽으로 쓴다. 판단이 필요한 건은 반드시 사용자에게 올린다.

## 자동 처리

**2026-11-02에 사용자가 승인 없는 자동 쓰기를 허용했다 — 아래 조건을 전부 만족하는 건만이다.** 하나라도 어긋나면 그 건은 보고하고 멈춘다.

### 먼저 — 공통 전제 6가지

**이 중 하나라도 어긋나면 자동 처리를 전면 중단하고 전부 수동으로 올린다.** 자동 처리의 위험은 "틀린 판단"이 아니라 **"수집이 반쪽인 걸 모른 채 판단"** 이다.

1. **수집 완전성 자기검사를 통과했다**
   - 에어비앤비 호스팅 목록: 헤딩의 `예약 N건`과 파싱한 행 수가 **같다** (29건인데 28행만 그려진 적이 있다)
   - 익스트라넷: 각 조회 구간의 결과가 **50건 미만**이다. 50건이면 잘렸을 수 있으니 구간을 쪼개 다시 조회한다
   - 익스트라넷: **결과가 0건인 구간은 반드시 더 좁은 구간으로 쪼개 재조회한다.** 넓은 구간은 오류 없이 **조용히 0건을 반환한다** — 2026-11-02에 `2027-07-01~2028-12-31`이 0건이었고 `2027-07-01~2027-12-31`로 좁히니 7건이 나왔다. 다올도 같은 식으로 1건을 놓쳤다. **그래서 조회 구간은 처음부터 6개월 이하로 끊는다**
   - 국적 검증을 돌릴 때 `NATIONALITIES` 추출 개수가 **51이 아니면 검증 실패로 본다.** 목록이 빈 채로 비교하면 모든 값이 "목록 밖"으로 뜨거나 그 반대가 된다. 정의는 **쌍따옴표**다(`"한국", "일본", …`)
   - iCal 3개: 파싱한 이벤트마다 **예약코드가 비어 있지 않다** (바이너리로 안 읽으면 전부 빈다)
   - **파싱 결과를 담은 변수를 파일로 쓴 직후, 파일을 다시 읽어 건수를 확인한다.** 2026-11-01에 REPL 스코프 섀도잉으로 7행이 조용히 누락돼 **오탐 5건**이 나왔다. 그 5건이 자동 삭제에 걸렸다면 멀쩡한 미래 예약이 지워졌다
2. **`bookNumber`가 있는 건만.** 비어 있으면 날짜 매칭이고 그건 추측이다 — 자동 처리 대상이 아니다
3. **한 예약이 두 객실을 동시에 잡은 건은 수동.** 익스트라넷 `객실` 열이 `1 x 2층 아라, 1 x 3층 마루` 형태로 나온다(2026-11-02 `5908831200`, 취소분이라 영향은 없었다). 객실→숙소 매핑이 깨지고 **같은 예약번호를 두 컬렉션에 넣어야** 하므로 자동으로 처리하지 않는다
4. **같은 `bookNumber`에 신규와 취소가 함께 있으면 수동.** 2026-10-30에 晶博 佟이 마루를 예약하고 같은 날 취소해 순영향이 0이었다. 처리 순서가 뒤바뀌면 유령 예약이 남는다
5. **자동 삭제가 3건을 넘으면 멈추고 보고한다.** 한 번에 여러 건이 삭제 대상이면 취소가 몰린 것보다 **수집 오류일 확률이 높다**
6. **쓰기 전에 영구 백업한다.** 세션 스크래치패드는 세션이 끝나면 사라지므로, 자동 쓰기는 `~/.arangjae-backups/YYYY-MM-DD/`에도 남긴다 (`mkdir -p`). 스크래치패드 백업은 그대로 하되 이쪽이 되돌릴 근거다

### A. 취소 → 자동 삭제

세 조건을 **모두** 만족할 때:

- **취소 메일을 받았다** — 에어비앤비 `취소됨: …(코드)` 또는 부킹닷컴 `취소된 예약 안내! (번호, 날짜)`
- **채널에서도 확인된다** — 익스트라넷 `예약 상태`가 `취소됨`이거나, 에어비앤비 iCal·호스팅 목록에서 사라졌다
- 앱에 그 `bookNumber`가 남아 있다

→ 예약을 삭제한다. 그날 청소는 **기존 3조건**(`auto:true` · `cleaner` 빈 값 · 그날 퇴실하는 다른 예약 없음)을 만족할 때만 같은 배치로 지운다. **담당자가 배정돼 있으면 사람이 이미 일을 잡아둔 것**이므로 청소는 남기고 보고에 명시한다.

**메일 조건을 빼지 않는다.** 채널 조회 하나만 믿으면 2026-11-01의 오탐 5건이 그대로 삭제된다 — 그 5건에는 취소 메일이 없었다.

### B. 신규 → 자동 추가

다섯 조건을 **모두** 만족할 때:

- **신규 메일을 받았다** — 에어비앤비 `예약 확정 - …` 또는 부킹닷컴 `신규 예약 안내! (번호, 날짜)`
- **채널에 있다** — 익스트라넷 상태가 `OK …`이거나, 에어비앤비 호스팅 목록과 iCal에 둘 다 있다
- 앱에 그 `bookNumber`가 **없다**
- **날짜가 비어 있다** — 아래 정의대로
- **이름과 인원을 출처에서 읽었다.** 둘 중 하나라도 못 읽었으면 수동
- **신규 메일의 체크인 날짜가 채널과 같다.** 다르면 **첫 동기화 전에 변경이 끼어든 것**이므로, 같은 예약코드의 `예약 변경 완료` 메일을 찾아 확인한다 — 찾으면 **채널 날짜**로 추가하고(채널이 1차 소스다) 보고에 "신규 후 변경" 이라고 적는다. 못 찾으면 **수동.** 2026-11-02에 아라 `HM4KXTAYB2`가 이 경우였다(메일 7/29 → 채널 7/28~8/1)

→ 예약을 추가하고 **퇴실일 청소를 같은 배치**에 넣는다.

**"날짜가 비어 있다"의 정의:** 체크인 ~ **(체크아웃 − 1일)** 구간이 같은 숙소의 다른 예약과 겹치지 않는다. 비교 대상은 **앱의 기존 예약 + 같은 배치에서 추가할 다른 건**이다.

- **전환일은 겹침이 아니다.** A의 퇴실일 == B의 입실일은 정상이다. 체크인 날짜만 보고 판단하면 2박 예약의 둘째 날 겹침을 놓친다
- 겹치면 **쓰지 않고 올려서 묻는다.** 같은 방을 두 번 판 것일 수 있다

**국적을 확인할 수 없으면 기본값 `한국`으로 두고 추가한다**(2026-11-02 사용자 결정). 에어비앤비는 주 게스트 거주지가 안 나오거나 동반자 것만 나오는 경우가 잦다. **보고에 `국적 미확인` 목록을 따로 올린다** — 체크인 때 여권으로 고치면 된다. 국적이 `NATIONALITIES` 목록 밖의 나라면 역시 `한국`으로 두고 그 나라 이름을 보고한다. **목록 밖 값을 그대로 쓰지 않는다.**

### C. 변경 → 자동 처리하지 않는다

**2026-11-02에 수동 유지로 결정했다.** 변경은 신규와 같은 규칙으로 처리할 수 없다 —

- 변경은 기존 예약이 앱에 **이미 있는** 상태다. 원래 날짜는 "비어 있음"이 아니므로 손대지 않고, 새 날짜는 비어 있어서 추가된다 → **같은 예약이 2건**이 된다
- 올바른 처리는 `bookNumber`로 문서를 찾아 `updateMask`로 날짜만 고치고, **청소 문서를 옛 퇴실일에서 새 퇴실일로 옮기는** 3문서 연동이다
- 게다가 변경 요청이 **이미 앱에 반영돼 있던** 사례가 있었다 — 또 쓰면 되돌린다

→ 변경은 지금처럼 대조 보고에 올리고 승인을 받는다.

### 자동 처리한 뒤

**자동으로 썼어도 전부 보고한다.** 승인을 건너뛴 것이지 보고를 건너뛰는 게 아니다. 건마다 **무엇을 왜 썼는지 · 근거(메일 제목 + 채널 상태) · 영구 백업 경로**를 적고, §7 검증 4종을 똑같이 돌린다. 건너뛰고 수동으로 올린 건은 따로 묶어 **왜 자동 조건에 안 맞았는지** 쓴다.

- 다올 **에어비앤비 10건**: 예약 상세의 `Booking date`를 전부 읽었고 **최댓값이 2026-10-19**다
- 다올 **부킹닷컴 55건**: 익스트라넷 목록의 `예약 날짜` 열을 전부 읽었고 **최댓값이 2026-10-13**다
- 같은 기간 아랑재에는 신규가 10건 왔다(에어비앤비 2 + 부킹닷컴 8). 즉 메일 자체는 정상 수신되고 있고, **다올 건만 없다**

**그래서 "미확인"의 이유는 "메일이 안 온다"가 아니라 "판단할 예약이 없었다"다.** 수락 이후 생긴 다올 예약이 처음 나왔을 때 그 건의 알림 메일이 왔는지로 판단하고, 결과를 사용자에게 알린다. 그때까지 다올은 메일에 의존하지 말고 1·2번 경로로 본다.

## 0. 시작 전 — 부킹닷컴 로그인 확인

**수집을 시작하기 전에 이것부터 확인한다.** 에어비앤비·iCal·메일·앱을 먼저 다 훑고 나서 부킹닷컴에서 막히면 보고가 반쪽이 된다.

```js
// mcp__aside__repl
const probe = await openTab("https://admin.booking.com/");
await sleep(4000);
console.log(probe.url());   // account.booking.com/sign-in 으로 튕기면 로그아웃 상태다
```

**로그인 화면으로 튕기면 내가 직접 로그인을 시도한다.** 2026-10-29에 사용자가 허용했다. 사용자명·비밀번호는 Aside vault에 있고, **Aside는 저장된 비밀번호를 나에게 보여주지 않는다** — 제안 카드를 누르는 것까지만 할 수 있다(<https://docs.aside.com/help/passwords>: "saved passwords stay local and hidden from AI").

경로는 두 가지다. 먼저 (a)를 쓰고, 안 되면 (b)로 넘어간다.

- **(a) 로그인 페이지의 Aside vault 제안 카드를 누른다.** `snapshot(page, { interactive: true })`에 `iframe [origin="Aside Vault"]` 안에 `button "Fill saved login … ilaony@gmail.com"`으로 보인다. 설정이 `submitAfterAutofill: true`라서 채우면 알아서 넘어간다. **사용자명 → 비밀번호 2단계이므로 단계마다 한 번씩** 눌러야 한다
- **(b) `aside exec`에 위임한다.** [Aside 문서](https://docs.aside.com/help/troubleshooting)에 "If Aside reaches a sign-in screen, it can use allowed saved credentials through autofill"라고 돼 있다 — 저장된 자격증명을 쓰도록 **문서상 보장된 경로는 Aside 에이전트 쪽**이고, 내 REPL이 아니다

**6자리 코드 화면이 나오면 즉시 멈추고 사용자에게 올린다.** 코드는 vault에 없다. 2026-10-29 현재는 코드를 요구받지 않는데(사용자 확인), `auth.booking.com`의 `auth0-mfa-v2` 쿠키가 **2026-11-02 만료**인 7일짜리 기기 기억이기 때문이다. **그 전후로 코드가 한 번 다시 올 것으로 예상**한다.

**에이전트 자동 로그인은 2026-10-29 16:01에 (a)로 처음 성공했다.** 제안 카드를 **한 번** 누르자 사용자명·비밀번호 2단계가 모두 자동으로 넘어가 `groups/home`(그룹 메인)에 도착했고, 6자리 코드는 요구되지 않았다. 앞으로 실패하면 사용자에게 보고하고, 1·3·4번(에어비앤비·메일·앱)만 진행하고 보고에 **"부킹닷컴 미조회"를 명시**한다 — 반쪽 보고를 "이상 없음"으로 읽히게 두지 않는다.

**로그인 여부는 vault 감사 로그로 확인할 수 있다.** `~/.aside/password-manager/accounts/<id>/audit-logs/YYYY-MM-DD.log`에 한 줄씩 JSON이고, `actor` 필드가 있다. **단 REPL로 내가 누른 채우기도 `actor=user`로 찍힌다**(2026-10-29 16:01:20·21 두 줄 확인) — 그래서 이 로그로 사람과 나를 구분할 수 없다. 내 시도인지는 REPL 출력으로 판단한다.

**쿠키가 남아 있어도 로그아웃일 수 있다.** 2026-10-29 확인 결과 `bkng_sso_session` 만료는 2027-12-03인데도 `admin.booking.com/`이 로그인 화면으로 튕겼다 — 부킹닷컴이 서버에서 세션을 끊는 것이고, 하루에 여러 번 일어난다. **Aside 쪽 문제가 아니므로 Aside 설정을 손대지 않는다.**

에어비앤비는 이 문제가 없다.

## 1. 에어비앤비 — 호스팅 목록 + iCal

**호스팅 `예정` 목록이 1차 소스다. 세 숙소가 한 화면에 섞여 나오고, 각 행에 이름과 인원이 함께 있다.**

```js
// mcp__aside__repl. 이미 열린 탭이 있으면 그것을 쓴다.
const t = await listBrowserTabs();
const p = await attachBrowserTab(t.find(x => /airbnb/.test(x.url)).targetId);
await p.goto("https://www.airbnb.co.kr/hosting?tab=upcoming");
// "더 보기"를 버튼이 사라질 때까지 누른다
```

행 형식: `11월 9일~10일 진우 님의 일행(4명) [아라]광장시장/…`. 숙소는 리스팅 이름으로 가린다(`[아라]` / `[마루]` / `넓은 3룸`). 이름 사이에 `⁠`(word joiner)가 섞여 있으니 **제거하고 비교한다.**

**이 목록은 다 렌더되지 않을 수 있다.** 헤딩이 "예약 29건"인데 28행만 그려진 적이 있다. 그래서 **iCal로 교차검증한다.**

```bash
# 토큰은 .claude/settings.local.json 의 permissions.allow 에 있다 (git 추적 안 됨)
curl -sL "https://www.airbnb.com/calendar/ical/<리스팅ID>.ics?t=<토큰>&locale=ko" -o x.ics
```

iCal 파싱 요령:

- **반드시 바이너리로 읽어 디코드한다** (`open(f,"rb").read().decode()`). 파이썬 텍스트 모드는 `\r\n`을 바꿔버려서 RFC 5545 줄펼침(`\r\n ` → ``)이 안 먹고 예약코드가 전부 빈다
- `DTSTART`=체크인, `DTEND`=체크아웃, `DESCRIPTION`의 상세 URL에 **예약코드**(`HM…`)가 있다
- **에어비앤비 iCal은 연박을 병합하지 않는다** — 날짜·전환일이 정확하다
- iCal에 이름·인원·국적은 **없다**

**취소 탐지는 iCal 비교가 가장 확실하다.** 지난 실행의 `.ics`가 스크래치패드에 남아 있으면 **지금 받은 것과 diff**해서 **사라진 건 = 취소**로 본다. 실제로 이 방법으로 마루 `ryono`(`HMHTEZCMSD`) 취소를 잡았다.

이름·인원 외에 **국적**이 필요하면 상세를 연다:

```
https://www.airbnb.co.kr/hosting/reservations/details/<예약코드>
```

상세에서 **`거주지: …`** 가 국적의 근거다. 주의할 점:

- **주 게스트의 거주지가 표시되지 않는 경우가 많다** — 동반자 것만 나온다. 그러면 일행 기준으로 추정하고 **"동반자 거주지 기반"이라고 밝힌다**
- 아예 아무도 거주지가 없는 건도 있다 → **기본값을 그대로 두고 "확인 못 함"으로 보고한다.** 이름으로 국적을 정하지 않는다
- 상세 페이지에서 `님의 일행(N명)` 을 정규식으로 잡으면 **사이드바 목록의 첫 행이 걸린다.** 본문만 보려면 마지막 `체크인` 이후 구간으로 잘라서 찾는다

## 2. 부킹닷컴 — 익스트라넷

**숙소별로 따로 조회한다.** 화면 좌측 상단 숙소 선택기로 전환할 수도 있지만(전환하면 새 탭이 열리고 그 탭은 REPL에서 닫히지 않는다), **URL에 `hotel_id`를 넣어 바로 가는 게 빠르다.** `ses` 값은 열려 있는 익스트라넷 탭 URL에서 가져온다.

```
목록: .../extranet_ng/manage/search_reservations.html
        ?ses=<세션>&hotel_id=<id>&lang=ko&date_type=arrival&date_from=&date_to=
상세: .../extranet_ng/manage/booking.html?ses=<세션>&hotel_id=<id>&lang=ko&res_id=<예약번호>
```

**`res_id`는 예약번호와 같다.** 목록 표의 `예약 번호` 열을 그대로 넣으면 된다.

표 읽기:

```js
const t = [...document.querySelectorAll('table')].find(x => /투숙객 이름/.test(x.innerText));
// 데이터 행: th,td 가 9칸이고 2번째 칸에 "YYYY년"이 있는 행
```

- **표는 비어 있는 채로 먼저 그려진다.** 행 수만 보고 판단하면 빈 행을 읽는다. **셀에 내용이 채워질 때까지** 기다린다
- 하단 `예약 로딩 중...` 은 사라지지 않는 고정 행이다. 그게 없어지길 기다리면 안 된다
- 한 번에 약 50건에서 잘린다. 넘으면 **날짜 구간을 쪼갠다.** 넓은 구간은 오류(`앗, 오류가 발생했습니다`)가 난다
- **열 구성**: 투숙객 이름 / 체크인 / 체크아웃 / 객실 / 예약 날짜 / **예약 상태** / 요금 / 수수료 / 예약 번호
- 상태가 `OK …`면 유효, `취소됨`이면 취소다. **취소도 같이 읽어야** 앱에 남은 취소분을 잡는다
- 인원은 이름 칸에 `성인 N명, 아동 M명 (나이)` 로 붙어 온다. 앱의 `guests`는 **아동 포함 총원**이다
- **현재 숙박 중인 건을 놓치지 않도록** 도착일 기준 조회를 오늘보다 앞에서 시작한다(예: 30일 전부터)

**국적은 상세에서만 나온다** — 투숙객 이름 바로 아래 **2자리 국가 코드**(`ca`, `tw`, `it`, `nz` …). 요청사항이 있으면 메모에 넣을 수 있다.

**REPL은 120초 제한이다.** 상세를 여러 건 돌 때는 **4건씩 나눈다.** 한 번에 10건 이상 돌리면 연결이 끊긴 것처럼 실패한다.

## 3. 메일 — 보조 수단

1·2번이 1차 소스다. 메일은 **변경 요청/수락**처럼 캘린더에 안 나타나는 사건과, 최근 움직임을 빠르게 훑는 데 쓴다.

```js
await googleAccounts.print();   // 아랑재 = ilaony@gmail.com, 보통 uid 0
await gmail.search(uid, 'from:airbnb.com after:YYYY/MM/DD');
await gmail.search(uid, 'from:booking.com after:YYYY/MM/DD');
```

**처리 대상:**

| 제목 패턴 | 뜻 |
|---|---|
| `예약 확정 - OOO 님이 …체크인할 예정` | 에어비앤비 신규 |
| `예약 변경 완료` / `OOO님이 예약 변경을 요청합니다` | 에어비앤비 변경 |
| `취소됨: 11월 21일~23일 예약 건(HMHTEZCMSD)` | 에어비앤비 취소 — **제목이 이 형태다.** `예약 취소`로 찾으면 안 걸린다 |
| `Booking.com - 신규 예약 안내! (번호, 날짜)` | 부킹닷컴 신규 |
| `Booking.com - 취소된 예약 안내! (번호, 날짜)` | 부킹닷컴 취소 |

**무시:** 후기 요청·후기 등록, `예약 알림: …곧 체크인`(기존 예약 리마인더), `예약 메시지가 전송되지 않았습니다`(메시지 템플릿 발송 안내), 광고(`discover@airbnb.com`), 게스트 메시지(`express@airbnb.com`, `*@guest.booking.com`), 숙박업 호스트 다이제스트, 익스트라넷 계정·비밀번호 관련 안내.

변경 메일은 **`예약 변경 완료`가 온 것만 확정**이다. `변경을 요청합니다`만 있고 완료 메일이 없으면 수락 여부를 알 수 없으니 "확인 필요"로 올린다. Gmail은 제목이 같은 변경 완료 메일을 한 스레드로 묶으므로 **스레드의 모든 메시지**를 봐야 한다 — 게스트가 다를 수 있다.

**메일에 없는 필드는 추측해서 채우지 않는다.** **부킹닷컴 신규 메일은 제목에 예약번호와 체크인 날짜, 본문에 숙소명과 `hotel_id`를 준다** — 즉 **어느 숙소인지는 메일만으로 가린다**(2026-11-02 확인: 본문 상단에 `아랑재 arangjae`, 상세 링크에 `hotel_id=16131113`). 다만 **이름·인원·국적은 없으니** 상세가 필요하면 2번 경로로 간다. 빈 필드는 "값이 다름"이 아니라 **"출처에 없음"으로 따로 표시한다.**

## 4. 앱 데이터 조회

```bash
KEY=$(grep -o 'AIza[A-Za-z0-9_-]*' src/firebase.js)
B="https://firestore.googleapis.com/v1/projects/arangjae-manager/databases/(default)/documents"
for p in arangjae-ara arangjae-maru daol; do
  curl -s "$B/bookings-$p?key=$KEY&pageSize=500"
  curl -s "$B/cleaning-$p?key=$KEY&pageSize=500"
done
```

청소 컬렉션은 **문서 ID가 날짜 문자열**(`2026-11-10`)이다.

매칭은 **예약코드(`bookNumber`)가 있으면 그것으로** 한다. 세 숙소의 미래 예약에는 2026-10-28에 전부 채워뒀다. 없으면(대개 과거분) 숙소+체크인 날짜로 하고, **날짜 매칭은 추측이므로 결과에 그렇다고 표시한다.**

## 5. 대조 보고

표로 올린다 — 각 건마다 **출처 값 / 앱 값 / 제안 조치 / 근거(예약코드)**. 네 갈래로 분류한다:

1. **앱에 없음** → 추가 제안 (+ 퇴실일 청소 자동 등록)
2. **값이 다름** → 수정 제안, 어느 필드인지 명시
3. **취소됐는데 앱에 남아 있음** → 삭제 제안 (+ 그날 청소)
4. **이미 일치** → 한 줄로 "N건 일치"

숙소별로 나눠 쓴다. 판단이 필요한 건은 따로 떼어 **왜 애매한지** 쓴다.

**각 건을 `## 자동 처리`의 조건에 대입해 둘로 가른다** — **자동(승인 없이 쓸 것)** 과 **승인 필요**. 자동 쪽은 **먼저 쓰고 결과까지 함께 보고**하고, 승인 필요 쪽은 올린 뒤 **멈춘다.** 자동이 0건이고 승인 필요만 있으면 지금까지처럼 그냥 멈춘다.

## 6. 쓰기

**자동 처리 대상은 승인 없이, 나머지는 승인받은 범위만** 쓴다. **쓰기 전에 대상 문서를 스크래치패드에 백업한다** — 삭제·수정 모두. **자동 처리 건은 `~/.arangjae-backups/YYYY-MM-DD/`에도 남긴다**(§자동 처리 전제 6).

예약과 청소는 **한 배치로 원자적으로** 커밋한다 (앱의 `saveBookingWithCleaning` / `deleteBookingWithCleaning`과 같은 동작):

```bash
curl -s -X POST \
  "https://firestore.googleapis.com/v1/projects/arangjae-manager/databases/(default)/documents:commit?key=$KEY" \
  -H 'Content-Type: application/json' -d @writes.json
```

> zsh에서 `"$B:commit"`은 `:c` 파라미터 수정자에 먹혀 URL이 깨진다. **위처럼 전체 URL을 그대로 쓴다.**

지킬 것:

- **쓰기 전에 날짜 겹침을 검사한다.** 추가분이 기존 예약이나 다른 추가분과 겹치면 올려서 묻는다 — 같은 방을 두 번 판 것일 수 있다
- **일부 필드만 고칠 때는 `updateMask.fieldPaths`를 쓴다.** 마스크 없는 `update`는 문서를 통째로 교체해서 나머지 필드가 날아간다
- **새 문서 ID**는 앱과 같은 방식으로 만든다 (`genId`, `src/App.jsx`):
  `Date.now().toString(36) + Math.random().toString(36).slice(2, 7)`
- 필드 타입: `stringValue`, `integerValue`(JSON 문자열로), `booleanValue`
- **신규 예약이면 퇴실일 청소를 같은 배치에 넣는다** — 문서 ID는 퇴실 날짜, `{status:"scheduled", auto:true, cleaner:"", memo:""}`. 그날 청소 문서가 이미 있으면 덮지 않고 그대로 둔다
- **삭제할 때 그날 청소도 지울지는 확인하고 지운다** — `auto:true`이고 `cleaner`가 비어 있고 **그날 퇴실하는 다른 예약이 없을 때만**. 담당자가 배정돼 있으면 남긴다
- **예약코드를 `bookNumber`에 넣는다.** 에어비앤비 `HM…` 코드도 넣는다 — 앱은 채널을 구분하지 않고 "예약번호"로 표시하므로(`booking.bookNumber &&`, `src/App.jsx`) 코드 수정 없이 동작한다
- **국적은 `NATIONALITIES`(`src/App.jsx`) 목록에 있는 값만 쓴다.** 51개가 들어 있다. 목록에 없는 국가가 나오면 임의로 넣지 말고 사용자에게 알린다 — 목록 밖 값은 나중에 편집 모달을 열 때 조용히 바뀐다. 목록에 추가하려면 코드 수정 + main 커밋(Vercel 배포)이 필요하고, **추가 전에 이미 저장된 국적 값 전체를 조사해 빠지는 게 없는지 확인한다**
- 흔한 코드 → 앱 값: `kr`→한국 `jp`→일본 `cn`→중국 `tw`→대만 `hk`→홍콩 `mo`→마카오 `us`→미국 `ca`→캐나다 `au`→호주(거주지 표기는 "오스트레일리아") `nz`→뉴질랜드 `it`→이탈리아 `de`→독일 `fr`→프랑스 `sg`→싱가포르 `il`→이스라엘 `at`→오스트리아
- 옵션 4개(`earlyCheckIn`, `lateCheckOut`, `luggageBefore`, `luggageAfter`)는 **확정된 요청일 때만** 켠다. 게스트의 희망 체크인 시간이나 방 선호(고층·조용한 방)는 해당하지 않는다

## 7. 검증과 보고

쓴 뒤 해당 문서를 다시 읽어 반영을 확인한다. 더해서:

- 숙소별 **예약 건수와 청소 건수**가 예상대로 늘었는지
- 미래 예약에 **퇴실일 청소 누락이 0건**인지
- 출처의 유효 예약 **전부가 앱에 있는지**(예약번호 집합 비교)
- 저장된 국적 중 **목록 밖 값이 없는지**

무엇을 왜 썼는지와 **백업 파일의 전체 절대 경로**를 보고한다. 조회 실패나 판단 보류로 **건너뛴 건이 있으면 명시**한다.

**내가 연 탭은 닫는다.** 원래 열려 있던 탭은 건드리지 않는다. 익스트라넷 숙소 전환으로 열린 팝업 탭은 `page.close()`로도 닫히지 않으니, 남으면 사용자에게 직접 닫아달라고 알린다.

## 참고 — 채널별 함정

- **부킹닷컴 iCal은 쓰지 않는다.** 연박을 하나로 병합해서 중간 전환일(퇴실=입실인 날)이 사라지고, 그러면 그날 청소가 잡히지 않는다
- 부킹닷컴 취소 통보는 **예약번호만** 알려준다. 그래서 `bookNumber`가 유실되면 대조가 불가능하다
- 다올은 **체크인 17:00 / 체크아웃 12:00** 으로 아랑재(16:00 / 11:00)와 다르다. 앱은 날짜만 저장하므로 영향은 없다
- 청소 담당자는 다올이 주로 **김지영**, 아랑재 마루가 **이미영**이다. 자동 생성분은 `cleaner`가 빈 값이고, 배정은 사용자 몫이다
- Aside REPL은 **최상위 스코프가 계속 유지된다.** 호출마다 변수명을 새로 쓴다. **단 Aside가 재시작되면 스코프가 통째로 날아간다**(2026-11-02에 수집 중간에 겪었다) — 그래서 중간 결과는 모아두지 말고 **구간마다 파일에 쓴다.** 그리고 세션 폴더 밖의 파일은 읽지 못하니, 스크래치패드와 주고받을 때는 `pwd` 아래에 쓴 뒤 Bash로 복사한다
