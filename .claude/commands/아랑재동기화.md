Gmail의 채널 알림 메일을 읽어 **아랑재 아라/마루**의 신규·변경·취소 예약을 찾고, 앱(Firestore)과 대조해 차이를 보고한다.

조회 범위: 최근 **$1**일 (비어 있으면 7일).

## 가장 중요한 규칙

**대조 결과를 먼저 보고하고, 사용자가 승인한 뒤에 쓴다.** 조회·대조는 승인 없이 진행하되, Firestore 쓰기는 절대 먼저 하지 않는다.

이유: 메일과 앱의 차이는 단순 반영이 아닌 경우가 많다. 실제로 나온 유형들 —

- 앱에 이름이 `ㅇㅇ` 같은 플레이스홀더로 들어가 있어 덮어쓸지 판단이 필요했다
- 변경 요청이 **이미 앱에 반영돼 있어** 또 쓰면 되돌릴 뻔했다
- 메일의 국적이 앱의 선택 목록에 없어서 **코드 수정이 필요**했다 (마카오)

기계적으로 쓰면 틀린 쪽으로 쓴다. 판단이 필요한 건은 반드시 사용자에게 올린다.

## 절대 하지 말 것

**다올(`daol`) 데이터는 읽지도 쓰지도 않는다.** 다올은 에어비앤비·부킹닷컴 모두 **별개 계정**이고, 이 Gmail 계정에는 다올 알림이 들어오지 않는다. 다올 건이 보이면 잘못 읽은 것이다.

## 1. 메일 조회

`mcp__aside__repl`로 Aside 브라우저의 Gmail 세션을 쓴다. 먼저 계정 번호를 확인한다:

```js
await googleAccounts.print();   // 아랑재 = ilaony@gmail.com, 보통 uid 0
```

그 uid로 두 채널을 검색한다 (`YYYY/MM/DD`는 오늘에서 $1일 전):

```js
await gmail.search(uid, 'from:airbnb.com after:2026/10/20');
await gmail.search(uid, 'from:booking.com after:2026/10/20');
```

제목으로 가려낸다. **처리 대상:**

| 제목 패턴 | 뜻 |
|---|---|
| `예약 확정 - OOO 님이 …체크인할 예정` | 에어비앤비 신규 |
| `예약 변경 완료` / `OOO님이 예약 변경을 요청합니다` | 에어비앤비 변경 |
| `예약 취소` | 에어비앤비 취소 |
| `Booking.com - 신규 예약 안내! (번호, 날짜)` | 부킹닷컴 신규 |
| `Booking.com - 취소된 예약 안내! (번호, 날짜)` | 부킹닷컴 취소 |

**무시:** 후기 요청·후기 등록, `예약 알림: …곧 체크인`(기존 예약 리마인더), 광고(`discover@airbnb.com`), 게스트 메시지(`express@airbnb.com`, `*@guest.booking.com`), 숙박업 호스트 다이제스트.

제목만으로 부족하면 `gmail.getThread(uid, threadId)`로 본문을 읽는다. 본문에서 뽑을 것:

- **숙소** — 제목·본문의 `[아라]` / `[마루]`
- **체크인/체크아웃** 날짜
- **인원** — `성인 N명` (변경 메일은 `요청 게스트`가 최종값)
- **이름**, **국적** (에어비앤비는 게스트 프로필의 국가, 부킹닷컴은 상세의 국가 코드)
- **예약코드** — 에어비앤비 `HM…` 8~10자, 부킹닷컴 숫자 10자

변경 메일은 **`예약 변경 완료`가 온 것만 확정**이다. `변경을 요청합니다`만 있고 완료 메일이 없으면 수락 여부를 알 수 없으니 "확인 필요"로 올린다. Gmail은 제목이 같은 변경 완료 메일을 한 스레드로 묶으므로, 스레드의 **모든 메시지**를 봐야 한다 — 게스트가 다를 수 있다.

## 2. 앱 데이터 조회

API 키는 `src/firebase.js:9`에 있다.

```bash
KEY=$(grep -o 'AIza[A-Za-z0-9_-]*' src/firebase.js)
B="https://firestore.googleapis.com/v1/projects/arangjae-manager/databases/(default)/documents"
curl -s "$B/bookings-arangjae-ara?key=$KEY&pageSize=500"
curl -s "$B/bookings-arangjae-maru?key=$KEY&pageSize=500"
```

청소는 `cleaning-arangjae-ara` / `cleaning-arangjae-maru`이고 **문서 ID가 날짜 문자열**(`2026-11-10`)이다.

매칭은 **예약코드(`bookNumber`)가 있으면 그것으로**, 없으면 숙소+체크인 날짜로 한다. 날짜 매칭은 추측이므로 결과에 그렇다고 표시한다.

## 3. 대조 보고

표로 올린다 — 각 건마다 **메일 값 / 앱 값 / 제안 조치 / 근거(예약코드)**. 네 갈래로 분류한다:

1. **앱에 없음** → 추가 제안 (+ 퇴실일 청소 자동 등록)
2. **값이 다름** → 수정 제안, 어느 필드인지 명시
3. **취소됐는데 앱에 남아 있음** → 삭제 제안 (+ 그날 청소)
4. **이미 일치** → 한 줄로 "N건 일치"

판단이 필요한 건은 따로 떼어 **왜 애매한지** 쓴다. 그리고 멈춘다.

## 4. 승인 후 쓰기

승인받은 범위만 쓴다.

**쓰기 전에 대상 문서를 스크래치패드에 백업한다.** 삭제·수정 모두.

예약과 청소는 **한 배치로 원자적으로** 커밋한다 (앱의 `saveBookingWithCleaning` / `deleteBookingWithCleaning`과 같은 동작):

```bash
curl -s -X POST \
  "https://firestore.googleapis.com/v1/projects/arangjae-manager/databases/(default)/documents:commit?key=$KEY" \
  -H 'Content-Type: application/json' -d @writes.json
```

> zsh에서 `"$B:commit"`은 `:c` 파라미터 수정자에 먹혀 URL이 깨진다. **위처럼 전체 URL을 그대로 쓴다.**

지킬 것:

- **일부 필드만 고칠 때는 `updateMask.fieldPaths`를 쓴다.** 마스크 없는 `update`는 문서를 통째로 교체해서 나머지 필드가 날아간다
- **새 문서 ID**는 앱과 같은 방식으로 만든다 (`src/App.jsx:56`):
  `Date.now().toString(36) + Math.random().toString(36).slice(2, 7)`
- 필드 타입: `stringValue`, `integerValue`(JSON 문자열로), `booleanValue`
- **신규 예약이면 퇴실일 청소를 같은 배치에 넣는다** — 문서 ID는 퇴실 날짜, `{status:"scheduled", auto:true, cleaner:"", memo:""}`
- **삭제할 때 그날 청소도 지울지는 확인하고 지운다** — `auto:true`이고 `cleaner`가 비어 있고 **그날 퇴실하는 다른 예약이 없을 때만**. 담당자가 배정돼 있으면 남긴다
- **예약코드를 `bookNumber`에 넣는다.** 에어비앤비 `HM…` 코드도 넣는다 — 앱은 채널을 구분하지 않고 "예약번호"로 표시하므로(`src/App.jsx:1104`) 코드 수정 없이 동작하고, 다음 대조가 날짜 추측 대신 코드 매칭이 된다
- **국적은 `src/App.jsx:35`의 `NATIONALITIES` 목록에 있는 값만 쓴다.** 목록에 없는 국가가 나오면 임의로 넣지 말고 사용자에게 알린다 — 목록 밖 값은 나중에 편집 모달을 열 때 조용히 바뀐다. 목록에 추가하려면 코드 수정 + main 커밋(Vercel 배포)이 필요하다
- 옵션 4개(`earlyCheckIn`, `lateCheckOut`, `luggageBefore`, `luggageAfter`)는 **확정된 요청일 때만** 켠다. 게스트의 희망 체크인 시간이나 방 선호(고층·조용한 방)는 해당하지 않는다

## 5. 검증과 보고

쓴 뒤 해당 문서를 다시 읽어 반영을 확인하고, 무엇을 왜 썼는지와 **백업 파일의 전체 절대 경로**를 보고한다. 조회 실패나 판단 보류로 **건너뛴 건이 있으면 명시**한다.

## 참고 — 채널별 함정

- **부킹닷컴 iCal은 쓰지 않는다.** 연박을 하나로 병합해서 중간 전환일(퇴실=입실인 날)이 사라지고, 그러면 그날 청소가 잡히지 않는다. 에어비앤비 iCal은 병합하지 않는다
- **부킹닷컴 익스트라넷**은 느리다. 표가 다 그려질 때까지 기다려야 하고, 한 번에 약 50건에서 잘리며(하단 `예약 로딩 중`은 고정 표시), 넓은 날짜 구간은 오류가 난다. 쓸 때는 구간을 나눈다
- 부킹닷컴 취소 통보는 **예약번호만** 알려준다. 그래서 `bookNumber`가 유실되면 대조가 불가능하다
